# Verification and traceability (`VER`)

## Test layers

| Layer | Runs where | Covers | Command |
|---|---|---|---|
| Core unit tests | Host, CMake/CTest, `firmware/test/core_tests.cpp` | `FW-DSP`, `FW-ATT`, `FW-SET`, `FW-FX` engine, patterns, parsing and presets, `FW-SEC-006/009/013/014`, `FW-TIME-004/006/010/013..017`, `FW-HW-002/004/006`, `FW-MCP` protocol logic, color/time helpers | `cmake -S firmware -B firmware/build -G Ninja && cmake --build firmware/build && ctest --test-dir firmware/build` |
| Emulator | WSL2, ESP8266 core host emulator, `firmware/scripts/emulate.sh` | The whole sketch with the host's network; LEDs logged (also to `~/.cache/tubeclock/host/emulator.log`); a 64 KB LittleFS with the device's block size, saved to a file in that directory | `npm run fw:emulate` (web server on `localhost:9080`) |
| API end-to-end | Node, `firmware/scripts/api-test.mjs`, against the emulator or a real clock. Reads the emulator's log for the `[leds]` and `[fx]` checks (skipped on a real clock), and starts the emulator again after the restart check | `FW-API`, `FW-FX` routes and persistence, `FW-SEC-005/006/007/011/013/014`, `FW-TIME-016` | `npm run fw:api-test [url]` |
| MCP end-to-end | Node, `firmware/scripts/mcp-test.mjs`: official `@modelcontextprotocol/client` `StreamableHTTPClientTransport`, plus raw HTTP for what a conforming client never sends, against the emulator or a real clock | `FW-MCP`, `FW-SEC-005/008/012/013`, `FW-BUD-003/004/005` | `npm run fw:mcp-test [url]` |
| Host unit tests | Node `node --test`, `src/*.test.ts` | `HOST-LIB`, `HOST-CLI`: detection, `TubeClockClient` and the built CLI against a local fake server (`src/fake-server.ts`) | `npm test` |
| Hardware | Manual, on the clock | `FW-HW`, `FW-OTA`, `FW-BUD-002`, `FW-TIME-009` | Checklist in this file |

## Rules

| ID | Rule | Status |
|---|---|---|
| VER-001 | Every requirement with status `Done` has at least one automated check that cites its ID, or is listed under the manual checklist below. `Partial` means the check is missing or covers only part. | Rule |
| VER-002 | A check cites IDs in its name or a comment on the line: C++ `// FW-ATT-004`, Node `check('FW-API-012 set tube 3 red', ...)`. One check MAY cite several IDs; one ID MAY have several checks. | Rule (core tests and API test cite IDs) |
| VER-003 | `rg '\b(FW|HOST|VER)-[A-Z]+-[0-9]{3}\b'` over `spec/`, `firmware/`, `src/` is the traceability report. A script (`scripts/spec-check.cjs`, Planned) lists `Done` IDs with no citation outside `spec/` and fails CI on any. | Planned |
| VER-004 | The API test restores every setting it changed and ends with `settings restored`. | Done |
| VER-005 | Tests never read `.env` values except the token, and never print it. | Done |
| VER-006 | The emulator run MUST show `[settings]` load, `[wifi] connected` and at least one `[leds]` line within 10 s; `fw:api-test` fails fast with a clear message if port 9080 is not listening. | Partial |
| VER-007 | The MCP end-to-end test uses the official TypeScript client, not hand-written JSON, and covers: `initialize` for each supported version, unsupported version `400`, `initialized` → `202`, `ping`, `tools/list` schema validity (each `inputSchema` compiles with a JSON Schema validator), each tool's happy path, bad color → `isError`, unknown tool → `-32602`, unknown method → `-32601`, batch → `400`, missing token → `401`, bad `Host` → `403`, bad `Origin` → `403`, oversized body → `413`, `GET /mcp` → `405`. | Done. Errors the client refuses to send or hides from the check (unknown method, batch, bad headers, oversized body) use raw HTTP. |
| VER-008 | Each `400` branch of each route has one API-test check (missing arg, out of range, junk). | Partial |
| VER-009 | The stale-header regression (FW-SEC-006) is covered twice: the core test with explicit lengths and the API test "no token right after a valid one is still 401". | Done |
| VER-010 | A change that adds a route or tool adds its checks in the same commit. | Rule |
| VER-011 | Hardware checklist results are recorded as a short note on the item in the checklist below, with the date and, where one applies, the firmware version. | Done for what has run so far (items 1, 2 and 7) |
| VER-012 | A strict-parser check: the API test fetches `/api/state` with `undici`/`fetch` (strict) and passes (FW-API-009). | Done |
| VER-013 | The API test checks that `version` matches `^\d+\.\d+\.\d+(-\d+-g[0-9a-f]+)?(-dirty)?$` and, when run against the emulator built from the current checkout, equals that checkout's `git describe` output (FW-API-031). A checkout that cannot see a `v` tag gets a bare hash (`v0.1.0` exists), so the test also accepts `^[0-9a-f]{7,40}(-dirty)?$`; the checkout comparison runs when the URL is `localhost`. | Done |
| VER-014 | Auth backoff (FW-SEC-014): the API test sends 6 bad tokens in a row and checks the 6th `401` takes ≥ 1 s while the first 5 take < 200 ms, then that a good token still succeeds at once. Runs last, since it costs seconds. | Partial (runs just before the restart check, which has to be last). **Gap:** the ≥ 1 s check is flaky on the emulator: the client often measures just under 1 s, with the MCP changes (22 of 60 samples, lowest 948 ms) and on the commit before them (38 of 40, lowest 405 ms). Cause not established. The emulator's `millis()` reads the wall clock, which is the first suspect, but a 30 s clock comparison in WSL showed no jump. |
| VER-015 | `beep=1`, `POST /api/restart`, blank-display-while-unset (FW-DSP-007) and the RTC path (FW-TIME-006) are checked on the emulator only as far as it can (argument accepted, `{ok:true}` returned, `[leds]` log shows all tubes off); the sound, reboot and RTC read are hardware checklist items. | Partial: `POST /api/restart` checked (the emulator exits). The emulator always runs on the host's clock, so it never shows blank tubes; FW-DSP-007 is covered by the core test and checklist 10 instead. `beep=1` is accepted and `beep=2` rejected (API test); the sound is checklist 11. The RTC's registers are host-tested (`testRtc`); the emulator has no RTC and reports `timeSource: "none"` (API test), and the read is checklist 10. |
| VER-022 | Last-accepted-sync check (FW-TIME-017), host tests on `judgeSync` with no RTC: first answer above the build epoch → accept; a second answer 3 days away from (first + elapsed) → needConfirmation, `rejectedSyncs` 1; a third agreeing with the second within 10 s → accept; a third agreeing with the *expected* time instead → accept and drop the pending value; a second answer 1 h away → accept. With both RTC and a last sync present, the reference is the last sync. API test on the emulator with the fake NTP server (VER-017): sane sync, then +3 days → `rejectedSyncs` 1 and `time` unchanged, then +3 days again → accepted. | Partial: host tests done (`testLastSyncReference`). **Gap:** the API test waits for VER-017. |
| VER-016 | The time-sync plausibility logic (FW-TIME-013/014) lives in the core as a pure function `judgeSync(candidate, current, buildEpoch, hasReference, pendingCandidate) → accept \| reject \| needConfirmation` (`hasReference`: a valid RTC at boot, or since FW-TIME-017 an accepted answer), unit-tested on the host: below the build epoch → reject; no reference → accept; reference and jump ≤ 24 h → accept; jump > 24 h once → needConfirmation; second candidate within 10 s of the first → accept; second candidate elsewhere → reject and replace the pending value. | Done (`judgeSync` takes microseconds and the pending value as a pointer, `nullptr` for none; `testJudgeSync`, `testTimeSync`) |
| VER-017 | Emulator: `emulate.sh` can point SNTP at a local Node fake NTP server (`firmware/scripts/fake-ntp.mjs`, UDP 123 → mapped to a high port) that answers with a configurable offset. The API test runs the firmware against it in three modes: sane time (state `lastSync` set, `rejectedSyncs` 0), time before the build epoch (`rejectedSyncs` 1, `time` unchanged, `[time] rejected` on serial), and a +3-day jump with an RTC value present (first answer rejected, second accepted). | Planned |
| VER-019 | Effects engine host tests (FW-FX-020..029, 070..071): every pattern is a pure function of `(effect, tube, t, seed)` and is tested for: determinism (same inputs → same RGB), palette interpolation at the stops and midpoints in both `hsv` and `rgb`, each `direction`'s `d(i)` table, `phase` (tube `i+1` shows tube `i`'s color `phase% × period` later for `ltr`), every `easing` at 0 / 0.5 / 1, `pulse` bounds, identical output across the `millis()` wrap, and that no pattern allocates (counted via a test allocator). A `rainbow` palette wave at `t=0` matches the old wave spec (tube 0 hue 0, tube 1 hue 330; by FW-FX-006 exactly 331.2, so the test takes 329..333). Each built-in preset parses and validates. | Done (`testEffectParse`, `testEffectMath`, `testEffectPatterns`, `testPresets`; the wrap test runs through `EffectClock`, which extends `millis()` to 64 bits). |
| VER-020 | API test (FW-FX-060..069): `PUT /api/effect` with a partial body keeps other fields; unknown field, bad palette entry, `period=99`, `phase=101`, 9-stop palette, 1025-byte body → `400`/`413` naming the field; `POST /api/preset?name=ocean` sets `preset:"ocean"`, a following `PUT /api/effect` clears it; `PUT /api/preset?name=mine` then `GET /api/presets` lists it with `builtin:false`, saving a 17th → `507`, `DELETE` of a built-in → `403`, of `mine` → `200`; `POST /api/tube` switches to `tubes`; `/api/display` round-trips each field and rejects `fadeMs=20`; an attention flash during `rainbow-wave` shows the flash color on every tube and the effect is back afterwards (two `[leds]` lines ≥ 1 s apart differ); digits in the `[leds]` log never change between frames within one second (FW-DSP-025); after `fw:emulate` restarts, the active effect and user presets are still there (FW-FX-050). | Done. The API test also covers `415`, the debounce (FW-FX-051) and 16 full-size presets on the device's file-system geometry. The log checks need the emulator. |
| VER-021 | Frame budget (FW-FX-072): the emulator logs `[fx] frame max=<us>`; the API test fails if any pattern's max exceeds 5000 µs on the host (a loose proxy; the real check is the device log in checklist 15). | Done on the emulator: besides once a minute, the line is logged when the effect changes, for the pattern just left (`[fx] frame max=<us> pattern=<name>`), so the test needs no minute per pattern. |
| VER-018 | The configured server list is checked at build: `build.sh` fails if `TUBECLOCK_NTP_SERVERS` contains `pool.ntp.org` or more than 3 entries (FW-TIME-010). | Done (env var `TUBECLOCK_NTP_SERVERS`; checked by hand, no automated check runs `build.sh`) |

## Manual hardware checklist

1. Stock image backed up and restorable (FW-OTA-008). Result 2026-11-06/07: backed up to `clock/backups/`; restoring it has not been tried.
2. Pin-finder identifies the LED pin, chain order and color order (FW-HW-004); the layout table is committed (FW-HW-005). Result 2026-11-06: GPIO 13, GRB, chain order read from video and committed as `LedLayout::ct001()`.
3. All six tubes show the right digits at `12:34:56` in both hour modes (FW-DSP-003).
4. Brightness 0, 99, 255 look as expected; attention flash and blink visible (FW-ATT-002/003).
5. Seconds tick within ~100 ms of a phone clock (FW-TIME-009).
6. Power cycle keeps colors, brightness, hours, tz (FW-SET-003).
7. OTA from the PC succeeds and the clock comes back with its settings (FW-OTA-005). Result 2026-11-07: `npm run fw:ota` succeeded and the clock came back reporting `0.1.0-7-g1055b61`; its settings surviving has not been checked.
8. `freeHeap` ≥ 20 KB at idle (FW-BUD-002); image size within FW-BUD-001. The firmware has no `freeHeap` yet (FW-API-038 is Planned), so the heap half cannot be read.
9. Wi-Fi drop (router off 1 minute): display keeps running, clock reconnects (FW-SEC-017).
10. Power on without Wi-Fi: tubes show the RTC time within 2 s (FW-TIME-006); with a fresh RTC they stay blank (FW-DSP-007).
11. `beep=1` sounds two short pulses; a button press ends a running flash (FW-ATT-010/011).
12. `POST /api/restart` reboots and the clock is back on mDNS within 15 s (FW-API-018).
13. With the router's DNS pointing `time.cloudflare.com` at a fake server answering 1990, the clock keeps its RTC time and logs the rejection; restoring DNS resyncs within the hour (FW-TIME-013/015).
14. `preset use rainbow-wave`: the band visibly moves left → right, every tube fades (no steps), digits stay put as colors pass; `effect set wave --direction rtl` reverses it; an attention flash interrupts and the wave continues afterwards (FW-FX-022, FW-FX-070).
15. Every built-in preset for 1 minute each: no visible stutter, `[fx] frame max` stays under 5000 µs, free heap does not drop between presets (FW-FX-072/073). The firmware has no free-heap reading yet (FW-API-038 is Planned), so that part cannot be checked.
16. `display --transition crossfade --fade 300`: digit changes fade; `--seconds off` blanks tubes 5–6 while the colors keep flowing across them (FW-FX-032/033).
17. `node firmware/scripts/mcp-test.mjs <url>` passes against the real clock (FW-MCP). Not run yet.
