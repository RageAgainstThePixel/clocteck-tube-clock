## Time sync hardening

NTP is unauthenticated, and NTS (RFC 8915) needs TLS 1.3 key exchange, which is not practical on the ESP8285's RAM and flash. So the firmware limits who it asks and sanity-checks what it gets. The exposure is bounded: a spoofed time only changes the digits on the tubes and the RTC. Nothing in the security model depends on the time: bearer auth (FW-SEC-005), OTA (FW-OTA-002) and the backoff timer (FW-SEC-014, which uses `millis()`) all work without it.

| ID | Requirement | Status |
|---|---|---|
| FW-TIME-010 | Servers are **trusted operators only**, default `time.cloudflare.com`, `time.google.com`, `time.nist.gov`, in that order. No `pool.ntp.org` or other public pools by default. The list is a build-time constant (`-DTUBECLOCK_NTP_SERVERS="a,b,c"`, up to 3, the lwIP `SNTP_MAX_SERVERS` limit) so a user can point at a local server instead. | Done. The default lives in the sketch; an override is the environment variable `TUBECLOCK_NTP_SERVERS="a,b,c"` read by `build.sh`, which rejects `pool.ntp.org`, more than 3 entries, empty entries and anything but host-name/IP characters (VER-018), and passes it on as the `-D` define; a raw `-DTUBECLOCK_NTP_SERVERS` argument is refused so the check cannot be skipped. The sketch also `static_assert`s 1–3 entries. |
| FW-TIME-011 | Sync is automatic: the SNTP client starts as soon as Wi-Fi is up, retries on failure (lwIP backs off 15 s → up to 2 min), and resyncs every **1 hour** (the ESP8266 core default `sntp_update_delay_MS_rfc_not_less_than_15000()` = 3 600 000 ms; the firmware keeps that value explicitly rather than relying on the default). After a Wi-Fi reconnect a sync is requested at once. After a rejected answer (FW-TIME-015) the firmware asks again itself, with the server order rotated, 15 s later, doubling while rejections continue, up to the 1 h interval. | Done: `sntp_update_delay_MS_rfc_not_less_than_15000()` is overridden to return `TimeSync::kResyncMs`; `onConnected` re-runs `configTime`; retry back-off host-tested in `testTimeSync`. Hourly resync on hardware: manual checklist 13. |
| FW-TIME-012 | What the lwIP SNTP client actually does with several servers: it queries **one server at a time** and only moves to the next on timeout or a KoD/invalid reply; it never compares answers. So the second and third servers are **fallbacks**, not a vote. Cross-checking is done by the firmware itself (FW-TIME-014). | Done (statement of fact) |
| FW-TIME-013 | **Build-time floor:** `build.sh`/`emulate.sh` pass `-DTUBECLOCK_BUILD_EPOCH=<unix seconds at build>`. Any time from NTP or the RTC that is earlier than that is rejected. (This replaced the year ≥ 2024 check in FW-TIME-004.) The build fails when the define is missing. | Done for NTP (`judgeSync`, `TimeSync`, host-tested). The RTC side is in `TimeSync::begin` (host-tested) and is what FW-TIME-006 calls. |
| FW-TIME-014 | **Plausibility check against the RTC:** when the RTC held a valid time at boot, an NTP result that differs from the current system time by more than **24 h** is rejected unless the *next* sync (same or another server; the firmware rotates the server order before retrying so it is a different server when one is reachable) agrees with the first rejected value within 10 s. Two agreeing answers are accepted. Justification: a DS1307-class RTC drifts seconds per day, so a day-sized jump is either a dead coin cell (RTC wrong, and two consecutive NTP answers will agree) or a bad/spoofed reply (one answer, no agreement). Below 24 h a wrong reply is indistinguishable from drift and is accepted; the cost is a wrong display for at most one hour (FW-TIME-011). The pending value is kept relative to the monotonic `micros64()` counter, so "within 10 s" compares both answers at the same instant even though the retry comes 15 s later. A third answer is compared with the second (VER-016: a disagreeing answer replaces the pending one). | Partial: core logic done and host-tested (VER-016). `build.sh` sets the RTC pins by default (FW-TIME-006; a build without them passes "no valid RTC"). **Gap:** not seen working on the clock, and no end-to-end check until VER-017. |
| FW-TIME-015 | Checks run in the core's `settimeofday_cb` hook. A rejected result is **undone**: the previous system time is restored with `settimeofday`, the RTC is **not** written, `timeSource` stays as it was, and serial logs `[time] rejected <reason>: ntp=<iso> have=<iso> server=<name>`. An accepted result writes the RTC (FW-TIME-006) and logs `[time] synced from <server>`. | Partial: hook, undo (to the clock the firmware expected from its last accepted time plus `micros64()`) and both log lines are in the sketch; core part host-tested. lwIP does not expose which server answered, so `<server>` is a best guess from its per-server reachability registers (`answeringServer`, host-tested), `?` if none fits. The cb runs from the core's scheduler, so a rejected time can show for one 50 ms frame before it is undone. An accepted answer writes the RTC when its pins are set (FW-TIME-006). **Gap:** no automated end-to-end check until VER-017. |
| FW-TIME-017 | **Plausibility check against the last accepted sync.** Once any NTP answer has been accepted since boot, the firmware knows the *expected* time: that answer plus the monotonic time elapsed since (`micros64()`). A later NTP answer that differs from the expected time by more than **24 h** is rejected unless the next answer agrees with it within 10 s, exactly as FW-TIME-014; the RTC does not need to be valid for this rule. So a single spoofed resync can never move a synced clock by years. The first answer after boot with no valid RTC has nothing to compare to and faces only the build-epoch floor (FW-TIME-013). When both an RTC value and a last accepted sync exist, the expected time from the last sync wins (it is the more precise of the two). | Partial: core done and host-tested (`judgeSync` takes `hasReference`, which `TimeSync` sets once the RTC was valid or an answer was accepted; `testLastSyncReference`, VER-022). **Gap:** no end-to-end check until the fake NTP server exists (VER-017). |
| FW-TIME-016 | The state object gains `lastSync` (ISO-8601 UTC of the last accepted NTP result, or `null`) and `rejectedSyncs` (count since boot) so a client can notice a clock that is being fed bad time. Every undone answer counts, including the first of a confirmed pair. | Done (`testTimeSync`; API test checks the fields' format). |
